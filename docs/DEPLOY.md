# 部署設計：CI 自動部署到 Instabox 測試機

> 狀態：設計稿，尚未實作。對應 [HOSTING.md](HOSTING.md)、[PHASE0.md](PHASE0.md) 的 WP0.12。
> 機器：Instabox `main`（4 vCPU／8 GiB／20 GiB，免費方案，範本顯示為 `standard`，需在機器上驗證內容）。
> Instabox 內容依 2026-11-08 閱讀的官方文件整理，以官方為準。

## 1. 目標與原則

1. 合併進 `main` 且測試通過後，自動把這一版部署到 `esg.finrod.xyz`。
2. **在 CI 建置、把成品送上機器**：機器只負責解壓、遷移、切換，不裝 Composer／Node，也**不持有任何 GitHub 憑證**。機器磁碟只有 20 GiB，這樣也最省空間。
3. 每次部署都先備份、可驗證、可回滾，過程有紀錄。
4. 秘密只放在兩個地方：GitHub 的環境機密（Instabox API 金鑰）、機器上的 `.env`（應用程式設定）。不進儲存庫。
5. 測試站只放假資料；部署流程不處理真實資料。

## 2. 流程

```
PR ──▶ CI 測試（Pint、Larastan、Pest：SQLite 與 MySQL）
        │ 通過並合併到 main
        ▼
   建置成品（composer --no-dev、npm 建置、打包 tar.gz、計算 SHA-256）
        ▼
   部署工作（環境 test，使用 Instabox API 金鑰）
        ▼   instabox exec main --stdin -- receive.sh <版本> <SHA-256>
   機器 main：
     1. 驗證 SHA-256
     2. 解壓到 /data/releases/<時間>-<版本>/
     3. 連結共用目錄（.env、storage、資料庫）
     4. 備份資料庫與儲存目錄（VACUUM INTO）
     5. 執行遷移
     6. 切換 current 符號連結、重載服務
     7. 本機冒煙測試（機器內部，不經公網）
     8. 失敗 → 回到上一版並還原備份
```

- 成品以標準輸入串流傳到機器（Instabox 的 `exec --stdin` 支援二進位，上限 5 GiB），不需要先上傳再放到特定路徑。
- 保留最近 5 個版本供回滾，更舊的清除。
- 部署過程的輸出會顯示在 GitHub Actions 日誌，同時寫入機器上的 `/data/deploy/deploy.log`。

## 3. 觸發規則

| 事件 | 動作 |
|---|---|
| Pull Request | 只跑測試，不部署、不取得任何機密 |
| 合併到 `main` | 測試通過後自動部署到測試機 |
| 手動觸發 | 可重新部署指定版本，用於回滾或部署失敗後重試 |
| 分支與標籤 | 其他分支不部署 |

- 同一時間只允許一個部署（以並行群組序列化，新的排隊，不取消進行中的）。
- 來自 fork 的 Pull Request 不得取得機密；儲存庫應設定為不對 fork 的 PR 執行含機密的工作流程。

## 4. 免費方案與暫停的處理

你說明已有外部保活機制。依官方文件，要知道這些邊界：

| 事項 | 說明 |
|---|---|
| 保活只能防「閒置暫停」 | 免費方案連續運行最長約 8 小時（動態延長，最晚 8 小時），到了就暫停，**保活擋不住** |
| 最長運行暫停後有冷卻 | 第 1 次約 5 到 20 分鐘；連續第 2 次約 60 到 75 分鐘；第 3 次起約 120 到 135 分鐘。冷卻期間任何喚醒方式都被拒絕 |
| 估算可用比例 | 若保活使機器每次都跑滿 8 小時，穩定後約每 10 小時中有 8 小時可用（約八成），每天會有 2 次左右、各約 2 小時的中斷（依官方冷卻規則推算，非實測） |
| 單向喚醒 | 公開連接埠的請求、SSH、`exec`、`wake` 可喚醒；經 Cloudflare Tunnel 的請求不會 |
| 保活的措施不算「工作」 | 官方說明續租活動租約與喚醒請求不會延長運行時間窗 |

對部署的影響：
- 部署工作會呼叫 `exec`，必要時自動喚醒機器（最多等 45 秒）。
- 若遇到冷卻，Instabox 回傳可重試的 `409 machine_cooldown`，並告知剩餘秒數。部署工作最多等待 30 分鐘後重試，仍在冷卻就**失敗並在日誌寫明冷卻結束時間**；冷卻結束後可手動重新觸發同一版本。
- 部署是「可重複」的：同一版本重跑會得到相同結果。
- 提醒：請確認你的保活方式符合 Instabox 使用條款，且不會觸發它的自動濫用偵測（偵測到會鎖定機器至多 24 小時）。

## 5. 機器端結構（一次性初始化）

```
/data/
├── deploy/
│   ├── receive.sh        接收成品並部署（由 CI 呼叫）
│   ├── rollback.sh       手動回滾
│   └── deploy.log        部署紀錄
├── releases/<時間>-<版本>/   每個版本一個目錄（保留 5 個）
├── current → releases/…      目前版本（符號連結）
├── shared/
│   ├── .env              應用程式設定（只存在機器上）
│   ├── storage/          私有儲存（佐證檔、報表）
│   └── database/         SQLite 檔
└── backups/              每日與部署前備份（保留 30 份）
```

- 執行環境：Docker Compose（php-fpm 與 nginx），讀取 `current` 的程式碼並掛載 `shared/`；容器設 `restart: unless-stopped`。映像只在 Dockerfile 變更時重建，日常部署不重建映像。
- 與 CI 版本一致使用 PHP 8.3 的映像（Debian 13 套件庫的 PHP 版本可能不同，用容器以確保一致）。
- nginx 監聽機器內 `:80`，也就是 Tunnel 的入口。
- 初始化腳本由我寫進儲存庫（`deploy/bootstrap.sh`），你在機器上執行一次，並手動建立 `.env`（`APP_KEY` 由指令產生；初始管理員在安裝時互動輸入，不寫入任何檔案）。

**機器實測結果（2026-11-08，以唯讀指令檢查機器 `main`）**

| 項目 | 結果 | 影響 |
|---|---|---|
| 範本 | `agent-browser`（版本 2026-10-15.4） | 預裝 Docker 與 Compose |
| 作業系統 | Debian 13 (trixie)，核心 6.18.54-instabox | 主機無 PHP，使用容器可行且需要 |
| CPU／記憶體 | 4 vCPU／約 7.9 GiB（閒置時約用 470 MB） | 綽綽有餘 |
| 磁碟 | 根碟 16 GB（已用 4.1 GB，可用 11 GB）；資料碟 `/data` 20 GB（幾乎全空） | 程式、資料、備份放 `/data`；Docker 映像在根碟 `/var/lib/docker`，約 11 GB 可用，足夠，但須監控 |
| Docker | 29.8.2；Compose v5.6.0；儲存驅動 overlayfs | 可用 |
| Node | v22.23.3 | 主機不需要，CI 建置 |
| cloudflared | 版本 2026.10.7，systemd 服務 `active` | 與 Tunnel 已連線一致 |
| 使用者與權限 | 登入使用者為 `user`，可無密碼 sudo | 可安裝與設定服務 |
| 監聽埠 | 目前沒有服務監聽 80（先前測試頁已停止） | 之後由 nginx 容器接手 |
| 運行設定 | 閒置暫停 1800 秒、`maxRunMinutes` 目前 120（免費方案的動態時間窗）、無冷卻 | 與文件描述一致 |

結論：第 5 節的假設成立，不需調整結構。唯一需要留意：Docker 映像放根碟，部署與清理要避免映像累積（部署腳本定期執行 `docker image prune`）。

## 6. GitHub 與 Instabox 設定（由你執行）

1. **建立受限的 Instabox API 金鑰**：只給 `machines:write`（含 exec、檔案、喚醒；不含刪除與工作區管理）。金鑰只顯示一次，請直接放進 GitHub，不要貼給我。
2. **GitHub 儲存庫設定**：
   - 建立環境 `test`，把金鑰存為該環境的機密 `INSTABOX_API_KEY`，並限制只有 `main` 分支可使用。
   - 儲存庫設定中關閉「fork 的 Pull Request 執行工作流程」。
   - `main` 開啟分支保護：必須通過 CI 才能合併。
3. 金鑰外洩或人員異動時，到 Instabox 後台撤銷並重新建立。

## 7. CI 使用哪種執行器

- 你已把 Instabox 的 GitHub 整合接上，可用 `runs-on: instabox-medium`。
- **免費方案同時只能有 1 台運行中**，`main` 正在運行，CI 暫時機器可能被拒絕或排隊。因此建議：
  - **測試與建置用 GitHub 提供的執行器**（`ubuntu-24.04`），穩定且不佔 Instabox 名額；
  - **部署工作也在 GitHub 執行器上**，只是用 Instabox CLI 呼叫 `main`。
- 想用 `instabox-medium`，先用一個簡單的測試工作流程驗證，並用 `instabox ci` 查看有無排隊或被拒；驗證通過再切換。

## 8. 安全

| 項目 | 做法 |
|---|---|
| 金鑰最小權限 | 只給 `machines:write`；僅限 `main` 分支的 `test` 環境使用 |
| 第三方 Action | 以提交雜湊釘選版本，不用浮動標籤 |
| 成品完整性 | 傳輸後在機器驗證 SHA-256 |
| 機器不持有 GitHub 憑證 | 成品由 CI 推送 |
| 秘密不入日誌 | 日誌遮罩機密；腳本不印出 `.env` |
| 記錄 | 每次部署寫入版本、時間、結果、操作來源 |
| 風險提醒 | Instabox 文件指出擁有 `machines:write` 的金鑰可在機器上執行程式，因此該金鑰要視為高權限 |

## 9. 部署驗收標準（對應 WP0.12）

- [ ] 合併到 `main` 且測試通過後，無需人工介入就把新版本部署到測試機，`esg.finrod.xyz` 顯示新版本（頁尾顯示版本與時間）。
- [ ] 只提 Pull Request 時不會部署，工作日誌中沒有取得任何機密。
- [ ] 成品雜湊被竄改時，機器端拒絕部署並回報。
- [ ] 刻意讓遷移失敗：自動回到上一版與還原備份，網站持續可用，日誌說明原因。
- [ ] 部署前後都有備份；備份可實際還原（與 WP0.10 的還原演練合併驗證）。
- [ ] 同時觸發兩次部署，第二次排隊等待，不互相覆蓋。
- [ ] 機器處於暫停狀態時，部署會自動喚醒並完成。
- [ ] 機器處於冷卻時，部署等待後以清楚訊息失敗（含冷卻結束時間）；冷卻結束後手動重跑成功。
- [ ] 只保留最近 5 個版本與 30 份備份；磁碟使用率在驗收時維持在安全範圍。
- [ ] 手動回滾腳本能在 2 分鐘內回到上一版。
- [ ] 儲存庫、日誌與文件中搜尋不到任何金鑰或密碼。
