# 雲端測試主機規劃

> 狀態：規劃稿，尚未建置。目的：與你對齊測試主機的規格、存取方式與部署方式，確認後再動工。
> 對應 [PHASE0.md](PHASE0.md) 第 8 節與 [TECH_DESIGN.md](TECH_DESIGN.md) 第 2、10 節。

## 1. 為什麼需要這台主機

- 開發環境**沒有運作中的 Docker 服務**（只有 CLI），無法驗證 Docker Compose、nginx／TLS、備份與還原等容器相關驗收項目。
- 你與同事需要一個網址，用瀏覽器直接驗收畫面與流程，不必看截圖。
- 正式上線前，先在接近正式的環境演練「部署、備份、還原」。

## 2. 使用原則

1. **測試主機只放展示用的假資料。** 不放真實的能源、採購、財務或員工資料。公司在 IPO 籌備期，盤查資料屬於敏感資訊，真實資料等正式環境確認後再上。
2. 測試帳號用假名（已決定）；初始管理員為陳思蒝，信箱在安裝時由本人輸入，不寫進文件或程式碼。
3. 不把任何密碼、金鑰、權杖貼在對話或寫入儲存庫。
4. 主機可隨時重建：所有設定由儲存庫的腳本與設定檔還原，不依賴手動調整。

## 3. 建議規格

| 項目 | 建議 | 說明 |
|---|---|---|
| 作業系統 | Ubuntu Server 24.04 LTS | 長期支援、Docker 與 PHP 生態成熟 |
| CPU／記憶體 | 2 vCPU／4 GB | 50 人規模與測試綽綽有餘；建置前端時記憶體不要低於 2 GB |
| 磁碟 | 40 GB SSD（可擴充） | 映像、日誌、備份與佐證檔。階段 1 之後若大量上傳佐證再擴 |
| 區域 | 台灣或鄰近亞洲區域 | 延遲低；日後正式環境的資料落地位置另行決定 |
| 網路 | 固定公網 IP 或可綁定網域 | 用於 HTTPS 與憑證 |
| 快照 | 啟用每日快照，保留 7 天 | 與應用層備份互補，不取代 |

以上為建議，實際以你的雲端供應商與預算為準。

## 4. 網路與存取

**防火牆（安全群組）**

| 埠 | 來源 | 用途 |
|---|---|---|
| 443 | 依下方存取模式 | 網站（HTTPS） |
| 80 | 公開 | 僅用於憑證申請與導向 HTTPS |
| 22 | **限定管理者固定 IP** | SSH 管理；不對全網開放 |
| 其他 | 全部關閉 | 不開資料庫埠或管理埠 |

**存取模式（請你選一個）**

| 模式 | 作法 | 優缺點 |
|---|---|---|
| A. IP 白名單（建議） | 防火牆只允許公司辦公室與你的 IP 連 443 | 設定簡單、風險最低；外出需另加 IP |
| B. 公開網址加額外驗證 | 全網可連，但在網站前加一道基本驗證，再進應用程式登入 | 方便，但攻擊面較大，只適合純假資料 |
| C. VPN | 公司 VPN 內才能連 | 最安全，但需要既有 VPN |

**網域與憑證**
- 建議使用公司網域下的子網域（例如 `carbon-test.<公司網域>`），由你在 DNS 加一筆 A 記錄指向主機 IP。
- 憑證用 Let's Encrypt 自動申請與更新；需要 80 與 443 可由外部連到，或改用 DNS 驗證。若採 IP 白名單模式，建議用 DNS 驗證或讓 80 僅對憑證驗證開放。
- 強制 HTTPS，並啟用 HSTS。

## 5. 主機端架構

```
使用者 ─HTTPS→ 反向代理（Caddy 或 nginx）─→ php-fpm 容器（Laravel）
                                              │
                          資料卷：SQLite 檔、私有儲存、備份、日誌
```

- 以 Docker Compose 執行，與 TECH_DESIGN 一致。
- 反向代理建議用 Caddy（自動憑證，減少維運）；若你的環境規定使用 nginx 也可，兩者我都能提供設定。**此項待你確認**。
- SQLite 檔與上傳目錄放在**具名資料卷**，重建容器不會遺失。
- 備份目錄與資料卷分開掛載，並在雲端磁碟快照範圍內。
- 時區設為 Asia/Taipei，系統時間以 NTP 同步（稽核紀錄與提醒依賴準確時間）。

## 6. 帳號與權限

| 帳號 | 用途 | 規則 |
|---|---|---|
| `deploy`（非 root） | 部署與維運 | 只用 SSH 金鑰登入，停用密碼登入；加入 docker 群組 |
| root | — | 停用遠端登入 |
| 應用程式（容器內） | 執行網站 | 非 root，僅對資料卷有寫入權 |

- 你把**公開金鑰**放到主機即可；私鑰留在你手上，任何情況都不需要傳給我。
- 主機端需要唯讀存取儲存庫（見第 7 節）時，使用「唯讀部署金鑰」，只授權這個儲存庫。

## 7. 部署方式（兩個選項）

**我無法從開發環境直接連到你的主機**（網路受白名單限制，也不會持有你的 SSH 私鑰）。所以部署由主機端「拉取」而不是我「推送」。

| 選項 | 做法 | 適合 |
|---|---|---|
| **A. 手動拉取（階段 0 採用）** | 我把部署腳本放進儲存庫；你在主機上執行一個指令，它會拉取最新程式、備份資料、建置、遷移、健康檢查，失敗自動回滾 | 簡單、可控，每次部署你都知道 |
| B. 自架 Runner 自動部署（之後可升級） | 在主機安裝 GitHub Actions 的自架 Runner，合併到指定分支後自動部署 | 省事，但需要把 Runner 與儲存庫權限管好；儲存庫必須是私有 |

部署腳本的行為（選項 A）：
1. 檢查工作樹乾淨、目標版本（標籤或分支）存在。
2. 部署前自動備份資料庫與儲存目錄。
3. 建置映像、執行遷移。
4. 健康檢查通過才切換；失敗則回到上一版本並還原遷移前備份。
5. 保留最近 5 個版本供回滾，並寫入部署紀錄。

我要知道部署是否成功，只有兩個途徑：你回報腳本輸出，或主機開放一個公開的健康檢查網址、並把該網域加入此環境的網路白名單。是否接受後者，請見第 12 節第 7 題。

## 8. 備份與還原

- **應用層**：每日以 `VACUUM INTO` 產生資料庫副本，連同私有儲存目錄打包，保留 30 份（PHASE0 WP0.10）。
- **主機層**：雲端磁碟每日快照，保留 7 天。
- **異地**：備份定期複製到另一個儲存位置（雲端物件儲存或另一台主機），以免主機與快照同時失效。測試主機可後補；正式環境必做。
- **還原演練**：階段 0 驗收時，必須在這台主機實際做一次完整還原並記錄步驟與耗時。

## 9. 營運與監控

- 系統更新：開啟自動安全更新（unattended-upgrades），每月檢視一次需重啟的更新。
- 日誌：應用與反向代理日誌輪替，保留 30 天；不記錄密碼與個資。
- 磁碟與記憶體：簡單的每日檢查，使用率過高時通知你。
- 健康檢查：只回報「正常或異常」，不揭露版本與內部資訊。
- 稽核鏈驗證排程每月一次，異常通知管理員。
- 信件：階段 7 才需要。屆時需要公司的 SMTP 或第三方寄信服務，另行決定。

## 10. 開通清單（你這邊要做的事）

請依序完成，並**只把「結果」告訴我，不要貼任何密碼或私鑰**：

- [ ] 建立主機（Ubuntu Server 24.04 LTS，規格如第 3 節），啟用每日快照
- [ ] 設定防火牆：443、80、22 依第 4 節；22 限定固定 IP
- [ ] 建立 `deploy` 使用者，放入你的 SSH **公開**金鑰；停用密碼登入與 root 遠端登入
- [ ] 安裝 Docker Engine 與 Docker Compose 外掛（我會提供安裝步驟與檢查指令）
- [ ] 設定網域的 DNS A 記錄指向主機
- [ ] 回報：供應商、區域、主機規格、網域名稱、存取模式（A／B／C）
- [ ] 儲存庫新增**唯讀部署金鑰**，並在主機放入對應私鑰（私鑰只存在主機上）

我這邊會準備：部署腳本、Docker Compose 設定、反向代理設定、主機初始化檢查腳本、部署與還原手冊。

## 11. 風險

| 風險 | 對策 |
|---|---|
| 主機被當成真實資料的存放處 | 第 2 節原則；系統頁尾在測試環境顯示「測試環境，僅限展示資料」橫幅 |
| 網站對全網開放遭掃描攻擊 | 預設採 IP 白名單；啟用登入節流與稽核；系統自動更新 |
| SSH 暴力破解 | 僅金鑰登入、限定來源 IP、啟用 fail2ban 或等效機制 |
| 憑證申請失敗導致無法 HTTPS | 先確認 80／443 與 DNS；備援使用 DNS 驗證 |
| 主機損毀 | 快照加應用層備份加可重建腳本 |
| 我無法連到主機而無法替你除錯 | 部署腳本輸出清楚的診斷資訊；你回報輸出即可；必要時再討論開放健康檢查網址 |
| 個資與資料落地 | 測試期只用假資料；正式環境的區域與委外安排另案決定 |

## 12. 需要你決定

1. 雲端供應商與區域是哪一家？
2. 存取模式選 A（IP 白名單）、B 或 C？
3. 網域名稱與誰負責設定 DNS？
4. 反向代理選 Caddy（建議）還是 nginx？
5. 部署採選項 A（手動拉取，階段 0 建議）還是直接做 B？
6. 是否同意在測試環境頁尾顯示「測試環境」橫幅，並只放假資料？
7. 是否接受由我定義的健康檢查網址（公開、只回正常或異常），並把該網域加入此環境白名單，讓我能在你部署後自行確認狀態？
8. 誰是這台主機的維運負責人（更新、備份檢查）？
